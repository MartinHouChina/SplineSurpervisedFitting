# v16 r2 回退与快速验证

已完成的 `v16_r2_rollback_fast_k4_56_r1` 验证部署通过率为 17.7%；同样本 53 条合成曲线配对通过率由旧 r2 的 83.0% 降为 1.9%。该配置重置 Selector/Decoder，Joint 仅 60 次更新，不能作为成功的旧模型微调。后续请使用 [完整热启动与 Keep 状态交互恢复档](v16_keep_state_recovery.md)。下文保留该历史诊断的参数和操作记录。

这次回退按**同一任务口径**选择：合成源内部节点 K=4–56，归一化欧氏 MSE 阈值 `1e-4`，网络 Kc=56。历史 r2 最佳已保存检查点的验证通过率为 390/450（86.7%），合成子集 243/300（81.0%），平均保留 K=37.51；但 K=56 边界是 0/25，合成曲线平均比标注多约 13 个节点。它只是此前同口径中较好的起点，**不是已解决高 K 可行性或最简性的模型**。

更高的旧 `v16_adaptive_k96.pt` 检查点确有 795/800（99.375%）的原生一次性部署通过率，但其任务为 K=4–20、阈值 `2.5e-5`、Kc=96，且精确训练源码没有提交到 Git；不能把它当作当前 K=4–56 问题的已复现回退版。v14、v15 的原生 one-shot 通过率在各自旧阈值下也低于这一值。

回退前已做一次[固定样本快检](../outputs/comparisons/rollback_r2_vs_pilot_k4_56_diagnostic.json)：每个源 K=4..56 抽 1 条，共 53 条，旧 r2 原生部署通过 44/53（83.0%，平均 K=43.00），近期 Kc56 pilot 通过 0/53（平均 K=32.64）。旧 r2 在 K>=45 仅 3/12 通过，K=56 不通过；从 K=34 起许多样本直接保留全部 56 个候选。因此“回退提高通过率”与“达到最简节点数”是两个不同结论；这个快检仅用于定位方向。

回退脚本固定 Git 提交 `48d8b4e` 的 r2 架构，在 `outputs/rollback_v16_r2_source/` 创建独立 worktree；当前分支和已有检查点不受影响。服务器必须具备这个提交的 Git 历史（可先运行 `git cat-file -e '48d8b4e^{commit}'` 检查）。它默认从原 r2 Proposal 检查点**只迁移编码器、参数头和候选头**，Selector/Decoder 重新训练。因此是同架构短训诊断，不是旧完整训练的精确重放。首次运行还要求当前仓库已包含三个真实数据 manifest 和该 Proposal 检查点。

在 Linux/3090、仓库根目录、已激活 PyTorch CUDA 环境运行：

```bash
bash scripts/run_v16_r2_fast_validation.sh \
  --device cuda \
  --run-name v16_r2_rollback_fast_k4_56_r1
```

默认 Proposal 1 + Joint 12 epoch、train 600、合成 val 160（内含 16 条 K=56 边界）、每个真实来源 val 20、batch 128；保留原源范围、阈值、认证参数、训练损失及安全/复杂度日程。Joint 12 代恰能完成原日程，但样本/训练代数较少，结果仅用于验证旧机制是否仍有较高部署通过率。可以先追加 `--dry-run` 检查命令；同名产物存在时脚本会拒绝覆盖，重跑请换 `_r2` 等新名字。若没有 Proposal 文件，可加 `--no-warmstart`，但收敛与训练耗时都不可与预热档直接比较。

结果位于 `outputs/checkpoints/<run-name>.pt`、同名前缀的 `.history.json` 和 `outputs/logs/<run-name>/`。脚本训练后还会在**同一组固定曲线**上配对评估历史 r2 与新短训检查点，输出 `outputs/logs/<run-name>/paired.json`：合成 K=4..56 每个 K 一条、三类真实曲线各 5 条，单列 K>=45 与 K=56；如只想先看训练，可加 `--skip-paired`。首先看整体、Synthetic、真实来源及 K=56 边界的 **原生一次性** MSE、通过率和 K；不要把额外数值修复、全保留 Proposal 或小样本对照的通过率混入 Ours。训练验证规模变了，不能直接把新百分比与旧 390/450 相减当作显著性结论；配对结果也仅是快速诊断，正式结论须扩大独立样本。
